# Proactive assistance in OdooClaw

How the assistant stops waiting to be asked: what triggers a suggestion, what it
knows when it makes one, and how it delivers it.

## The short version

**These are three different problems, and the expensive mistake would be to put
all three inside the model's prompt.**

| # | Problem | The real question | Solution |
|---|---------|-------------------|----------|
| 1 | **Trigger** | When does it speak? | Deterministic, counting in Odoo |
| 2 | **Knowledge** | What does it know about "how to help"? | Playbooks, retrieved **by area** |
| 3 | **Delivery** | Where, and with whose permission? | Private chat + anti-nuisance policy |

**The LLM does not decide when to speak: it drafts the sentence.** With small
local models, "you decide when to interrupt" produces an assistant that speaks
when it should not and stays quiet when it should speak. Everything that decides
whether the user is interrupted is deterministic and auditable.

## Why proactive assistance is not a RAG problem

The reasonable instinct is "drop in a RAG and be done". Measured against the
code, it does not work:

```
Search("verifactu")                              -> 1 result
Search("how do I configure VeriFactu in Odoo?")  -> 0 results
Search("verifactu configure")                    -> 0 results
```

`pkg/knowledge` passes the raw query to FTS5 `MATCH`, which joins terms with an
implicit AND and does not strip stop words. **A natural-language question finds
nothing.** Had the trigger depended on phrasing, it would have failed silently:
the assistant never speaks, nobody knows why, and it looks like "it does not
work".

The design consequence is that **the trigger does not use free text**. It
retrieves by **filtering on area** (a structured field) and text only ranks
within the area. That is why `SearchByArea(area, query, limit)` exists.

### The fix the knowledge base needed

`Add()` stored the metadata (area, module, risk) in `knowledge_meta`, but
`Search()` only returned title/content/tags/category: **the metadata was written
and could not be read back**. Filtering by area was impossible without
duplicating the store. Fixed with a `knowledge_id` column + a `LEFT JOIN` on
`rowid` (additive schema, backwards compatible).

Two details learned along the way, both silent:

- **FTS5 does not accept a table alias in `MATCH`**: `k MATCH ?` returns
  `SQL logic error: no such column: k`, the query falls back to `LIKE`, and the
  fallback does not read the metadata. The symptom is "the fix does not work"
  with no error at all.
- `Search` must name the full table (`knowledge MATCH ?`).

## The piece that was really missing: the reply token

This is the part that makes "it works" a sentence with content.

`pkg/channels/odoo/odoo.go` **rejects with 400 any message without a
`reply_token`**, and that token is generated by Odoo when *a human writes to the
bot*, is single-use, and expires. The Odoo module validates it in
`/odooclaw/reply`.

That gate is deliberate and correct: it is what makes it safe for the endpoint to
call `sudo().message_post()`. Its consequence, **by construction**, is that a
message nobody asked for is impossible: no human message → no token → no reply.

```
Today:  a human writes -> Odoo generates a token -> gateway replies   ✔
        nobody writes  -> no token              -> gateway stays quiet ✗  ← proactivity
```

Proactivity needs the opposite flow, so it **cannot reuse that token**. The
solution adds an explicit service credential (the same shared secret
`X-OdooClaw-Token` the webhook already uses) and a dedicated route that can only
post to the bot's private chat with a user — **never into the chatter of a
business record**. The single-use token is untouched: the requested path is not
weakened.

## How it is wired

```
Odoo view opened
   │
   ├─ 1. Odoo resolves the AREA          mail.odooclaw.area.resolve_area(model, view, action)
   │      and counts the signals         counters_for() -> {"unposted_invoices": 12}
   │
   ├─ 2. POST /odooclaw/signal  ──────►  Go engine (pkg/proactive)
   │                                       ├─ opt-in?  hours?  daily cap?  cooldown?
   │                                       ├─ the area's playbook above its threshold
   │                                       └─ dedupe: the same offer is NEVER repeated
   │                                     ◄─── {speak, reason, playbook, message}
   │
   └─ 3. If speak               Odoo posts to the private chat (as the bot)
```

The engine decides; Odoo delivers. Keeping the post inside the request avoids the
window where a suggestion arrives after the user has already left.

### Alternative: delivery from the gateway

For triggers that do not come from a screen (a cron, another agent, an external
event), the reverse route exists:

```
Go engine  ──POST /odooclaw/notify──►  Odoo posts to the private chat
```

## The three components

### 1. Trigger — deterministic

`mail.odooclaw.area` maps a model/view/action to a **functional area** and its
counters. The rows are data: an administrator changes a threshold or a definition
without touching code.

A counter that fails **degrades to silence, not to an error**: a badly written
definition cannot break opening a view.

Deterministic resolution, from most specific to least: **action → view → model**.
The same screen must always resolve to the same area, or the cooldown becomes
inconsistent.

### 2. Knowledge — playbooks, not documentation

A playbook answers "what do I do when this happens": **an observable signal in an
area** + the offer that is made. It is **data**: the text is rewritten without
touching Go.

That matters more than it sounds. VeriFactu **has already changed once**: RDL
15/2025 (2 Dec) amended the 4th transitional provision of RD 1007/2023 and moved
the deadlines to **1 Jan 2027** (companies) and **1 Jul 2027** (the rest). The
2026 deadlines circulating on third-party sites are obsolete. That fact belongs in
an editable playbook and **never in the model's prompt**.

### 3. Delivery — with permission

The default policy is deliberately conservative:

| Rule | Value |
|---|---|
| Opt-in | **mandatory** |
| Cooldown per area | 24 h |
| Daily cap | 3 |
| Quiet hours | 21:00 – 08:00 |
| Dedupe | the same offer is never repeated |
| High-risk playbooks | require separate explicit authorisation |

An assistant that interrupts without permission is what makes people hate an
assistant.

**Every refusal returns an explainable reason**, so it is possible to audit why it
did **not** speak — which is the question asked most in production.

### Durability: state lives in SQLite

The policy state lives in SQLite (`pkg/proactive/store.go`), not in memory. An
in-memory map forgets its cooldowns on every restart, which turns "at most once
per area per day" into "once per deployment" — a promise the product cannot keep.
There is a test that pins this down.

The cooldown is recorded **only after a successful delivery**: if Odoo rejects the
message, the assistant is not left mute for 24 h because of a transient failure.

## Audience: who counts as an "internal DU user"

Nico set the rule: **any internal DU user**. Not a specific group, not a chosen
few — any employee. And explicitly **out**: portal users and the public user.

In Odoo that boundary is the standard `share` field, which is what Odoo itself
uses to separate employee from external (`base.group_user` sets it to `False`).
Using it aligns us with the platform instead of inventing a parallel definition:

| | |
|---|---|
| `share = False` | internal user (employee) ✅ |
| `share = True` | portal user ❌ |
| `active = False` | deactivated — must not receive new messages ❌ |

Verified against real Odoo 18 by creating the users and checking the outcome, not
by reading the documentation.

### Why the audience deserves its own model and not an `if`

It is `mail.odooclaw.audience`, with its own views and menu, for three reasons:

1. **It is a business rule, not a technical detail.** "Who counts as an employee
   here" changes (contractors, temporary staff, a subsidiary) and whoever holds
   that answer is not whoever writes Go.
2. **Getting it wrong leaks data.** The counters quoted in the offer are business
   figures — unposted invoices, bank lines. Showing them to a portal user would
   be a data leak dressed up as a helpful message.
3. **It has to be auditable.** When someone asks "why did it never offer me
   anything?", the answer must be inspectable without reading code.

### The deadlock this exposed

Defining the audience forced a look at the order of the checks, and there was a
design flaw that would have left the feature dead **with every test green**:

The engine required opt-in **before** making the first offer. But the first offer
*is* the question of whether the user wants help: with no offer nobody can accept,
and without accepting, the opt-in never turns on. The loop closed on itself, and
the tests did not see it because they enabled the opt-in themselves before
evaluating.

Measured, not assumed — this is what it looked like:

```
an internal user does not receive the initial offer:
  "the user has not enabled suggestions"
```

The distinction that fixes it separates three questions that were mixed into one:

| # | Question | Answer |
|---|---|---|
| 0 | Can this user receive help? | **Audience**: internal and active. If not, silence |
| 1 | Have they ever been asked? | **Invitation**: once only, and it is the question itself |
| 2 | Can it speak to them now? | **Policy**: cooldown, daily cap, quiet hours |

The invitation is the **only** thing that may be sent without prior opt-in, and it
carries its own guard: **one per user, forever**. It still respects quiet hours,
because waking someone at 3:00 to ask whether they want help is the fastest way to
get a no.

And that "once only" is stored in the **durable Store**, not in memory: the
engine's own documentation says all mutable state lives in the Store so that a
restart does not forget it. With the flag in memory, every deployment would have
asked again — and someone who already said "no" would have been pestered forever.

## The areas that ship

Areas ship **as data** in `data/odooclaw_proactive_<area>_data.xml`, so they
install themselves. None of the domains are written from memory: each one was
checked against a real Odoo 18 database, by creating records and confirming the
counter moves — and, just as important, confirming it does *not* move for a
record that must not match.

Every area follows the same shape: a counter that is cheap to compute, a
threshold that keeps it from nagging on a normal day, and a template that offers
a next step instead of a reproach.

| Area | Counter | Model | Counts |
|---|---|---|---|
| `contabilidad` | `unposted_invoices` | `account.move` | Customer drafts |
| `contabilidad` | `unposted_vendor_bills` | `account.move` | Vendor drafts |
| `contabilidad` | `unreconciled_statement_lines` | `account.bank.statement.line` | Unreconciled bank lines |
| `contabilidad` | `verifactu_unconfigured` | `ir.module.module` | VeriFactu not installed |
| `ventas` | `draft_quotations` | `sale.order` | Quotations in draft |
| `crm` | `stale_opportunities` | `crm.lead` | Opportunities with no activity planned |
| `crm` | `open_opportunities` | `crm.lead` | Opportunities not won |
| `crm` | `overdue_opportunities` | `crm.lead` | Expected closing in the past |
| `compras` | `draft_purchase_orders` | `purchase.order` | Purchase orders in draft |
| `inventario` | `negative_stock_products` | `product.product` | Negative stock |
| `rrhh` | `pending_leave_requests` | `hr.leave` | Leave awaiting approval |
| `expenses` | `draft_expenses` | `hr.expense` | Expenses not yet sent |
| `expenses` | `expenses_awaiting_approval` | `hr.expense` | Expenses submitted or approved |
| `projects` | `open_projects` | `project.project` | Projects not closed |
| `projects` | `overdue_projects` | `project.project` | End date in the past, still open |
| `projects` | `overdue_tasks` | `project.task` | Deadline past, not closed |
| `projects` | `waiting_tasks` | `project.task` | Tasks in the "waiting" state |
| `projects` | `urgent_tasks` | `project.task` | Tasks flagged urgent, still open |
| `fleet` | `unregistered_vehicles` | `fleet.vehicle` | Vehicles not yet registered |
| `fleet` | `vehicles_without_driver` | `fleet.vehicle` | Registered with no driver |

The threshold for each one lives in the playbook (`MinCount` in the engine, or
the KB entry), not in the domain: what changes the count is data, what changes
the decision to speak is policy.

## Phase 1: Accounting (loaded and verified)

Areas ship **as data** in `data/odooclaw_proactive_data.xml`, so they install
themselves. The domains are not written from memory: each one was checked against
a real Odoo 18 database with `account` installed, by creating records and
confirming the counter moves.

| Counter | Model | Counts | Threshold |
|---|---|---|---|
| `unposted_invoices` | `account.move` | Customer drafts (`out_invoice`/`out_refund`) | 5 |
| `unposted_vendor_bills` | `account.move` | Vendor drafts (`in_invoice`/`in_refund`) | 3 |
| `unreconciled_statement_lines` | `account.bank.statement.line` | Unreconciled bank lines | 1 |
| `verifactu_unconfigured` | `ir.module.module` | `l10n_es_edi_verifactu` not installed | 1 |

Two findings from that verification, both of the kind that fails **silently**:

- **The VeriFactu module in Odoo 18 is called `l10n_es_edi_verifactu`**, not
  `l10n_es_verifactu`. A counter pointing at the wrong name would return 0 forever
  and the user would simply never be warned. There is a test that pins it and goes
  red if the name changes.
- **`account.bank.statement.line.is_reconciled`** is the field that exists for
  "unreconciled" (and `account.bank.statement` does **not** exist as a model).

`verifactu_unconfigured` counts **the module not being installed**, which is the
real, verifiable state. Once the client installs it, the counter drops to 0 on its
own and the offer disappears: nothing has to be touched.

### How it is customised (without breaking anything)

The `data` uses `noupdate="0"`: the rows are **defaults that must keep arriving**
at existing installations. If they were protected, a counter added in a later
version would never arrive — the module would load cleanly and the signal would
simply never fire, which is invisible from the outside.

The convention that makes it safe: to change a threshold or a domain, **create a
new `mail.odooclaw.area` row**. The resolver picks by action → view → model, so a
more specific row wins. Do not edit a shipped row: an update restores it.

### About `account` not being installed

The base module depends only on `mail`, so Accounting can be loaded in an Odoo
without `account`. In that case the counters return **0 without logging an error**
(an area that does not apply yet is not a failure), and the tests skip cleanly
instead of failing. Verified under three conditions: without `account`, with
`account`, and a clean install.

### Where the areas live: one module per area

Keeping Accounting inside the base module would bind a generic Discuss
integration to `account.*`: the base declares `depends: ["mail"]`, yet its data
tied it to `account.move`, and those counters would have returned 0 silently in
any database without Accounting.

So the base ships the engine and each functional area ships in its own module:

| Module | Depends on | Ships |
|---|---|---|
| `mail_bot_odooclaw` | `mail` | the engine: area model, routes, audience |
| `mail_bot_odooclaw_account` | base + `account` | the Accounting areas |
| `mail_bot_odooclaw_sale` | base + `sale_management` | Sales areas |
| `mail_bot_odooclaw_crm` | base + `crm` | CRM areas |
| `mail_bot_odooclaw_purchase` | base + `purchase` | Purchase areas |
| `mail_bot_odooclaw_stock` | base + `stock` | Inventory areas |
| `mail_bot_odooclaw_hr` | base + `hr_holidays` | HR areas |
| `mail_bot_odooclaw_expense` | base + `hr_expense` | Expense areas |
| `mail_bot_odooclaw_project` | base + `project` | Project areas |
| `mail_bot_odooclaw_fleet` | base + `fleet` | Fleet areas |

Adding an area is then adding a module, and an installation only pays for the
areas it actually uses.

CRM is deliberately its own module rather than part of Sales. Two reasons, both
mechanical: the counters live on a different model (`crm.lead`, not
`sale.order`), and `sale_management` does **not** depend on `crm` — so
bundling them would force CRM onto every sales installation, which is exactly
the coupling this split exists to avoid.

### The overdue problem, and `$today`

Areas with a deadline — overdue tasks, projects past their end date,
opportunities past their expected closing — need a domain meaning "before
today". Writing a literal date works only on the day it is written and then
rots: the counter keeps returning a number, and it is the wrong one.

The engine resolves a `$today` placeholder at count time, anywhere in the
domain, so the definition stays true:

```json
{"overdue_tasks": {"model": "project.task",
                   "domain": [["date_deadline", "<", "$today"]]}}
```

This is deliberately narrow: no expression evaluation, no computed values, one
token. The alternative — letting administrators write Python in a data field —
would put arbitrary code execution in an XML record.

## Verification

What is measured, not assumed:

- **`go build ./...` clean, `go vet ./...` clean.**
- **47/47 Go packages green**, 0 failures.
- **42 tests** in `pkg/proactive` (engine, policy, audience, single invitation,
  durability across a restart, dedupe, delivery, the HTTP contract, the
  counters↔playbooks contract, and `$today` resolution).
- **Odoo tests on real Odoo 18 in Docker**, 0 failures, with T>0 — always check
  the run reports a **non-zero** number of tests, because a filter that matches
  nothing exits 0 and looks green.
- **Verification in both directions**: the code was deliberately mutated to check
  the tests really catch the failure — without area filtering the test goes red
  naming the wrong playbook; without `sudo()` they reproduce the real
  `AccessError`; with the wrong VeriFactu module name the pinning test fires;
  inverting the internal/portal flag drops 3 audience tests; and moving the
  invitation back into memory drops the durability test. A test that never goes
  red proves nothing.
- **Reproducible end-to-end demo** with the three audience cases: internal →
  invitation, portal → silence, unclassified → silence (fail closed).

The real bugs the verification found and that would not have been seen without
running against Odoo:

1. **`security.authorize()` raises `HTTPException`** to short-circuit. A generic
   `except Exception` turned **every 401 into a 500**. It has to be re-raised.
2. **`env.ref()` on a public route raises `AccessError`** when reading
   `res.users` (public user id=4): proactive posting needs `sudo()`.
3. **An area pointing at a model from a module that is not installed** logged a
   warning with a traceback on **every view open**. It now returns 0 in silence:
   an area that does not apply yet is not an error.
4. **`noupdate="1"` on the default data** stopped a new counter from reaching an
   existing installation: the module loaded cleanly and the signal simply never
   fired. The counters↔playbooks correspondence test caught it. It is now
   `noupdate="0"` plus the convention of creating a new row to customise.

## How to get it running

1. Install/update the modules you need (the base plus the areas you want).
2. Configure in Odoo: `odooclaw.reply_token` (the shared secret, already exists)
   and `odooclaw.proactive_url` (the engine); `odooclaw.allowed_ips` if an
   allowlist is used.
3. Load the areas into `mail.odooclaw.area` (or keep the defaults).
4. Start the proactivity engine.
5. Have users who want suggestions opt in.

## The metric that decides whether this works

**Offer acceptance rate.** If the user systematically closes the chat without
replying, the playbook or the threshold is wrong. That number outranks any
opinion.

## Rejected alternatives, with reasons

- **Vector RAG / embeddings** — not now. Small corpus, closed domain, and
  FTS5+BM25 is already there. It would add an embedding model and a vector store:
  exactly the opposite of "100% local, runs on 1 vCPU/2 GB". Re-evaluate if the
  corpus reaches thousands of entries.
- **A new SQLite store** — `pkg/knowledge` already is one; it would duplicate the
  retrieval.
- **Letting the LLM decide when to speak** — not deterministic, not auditable, it
  drifts.
- **Reusing the `reply_token` for proactivity** — impossible by design, and it
  would weaken the guarantee of the requested path.
- **The browser extension as the main channel** — only works on the web and with
  the extension installed; inside Odoo the channel is Discuss. Complementary.
